# 真人端到端 UI 验收方案（执行版）

> 用途：以"普通用户视角"对当前版本做 UI 端到端验收。本文件交给执行方（codex），由真人（我）在 UI 上实际操作，执行方只负责准备环境、按本方案提示我操作、并如实记录我提供的观察与原始证据，不做任何后台补链或代为推进。

## 一、目标与正式要求

对当前版本做**普通用户视角的 UI 端到端验收**：从 UI 配置并启动新 run，完成真实求助、人工输入回复、后续执行、原生结果及恢复检查。

- 测试期间**只通过可见 UI 和系统交互**推进，不使用后台接口补链。
- 先保留**正常使用体验**，再覆盖超时、取消、重复提交、中断、恢复。
- 所有结论附**原始操作证据**；无法观察的能力明确记为**证据不足**；失败和未覆盖**全部保留**。

## 二、硬约束（只通过 UI）

测试过程中**允许**：点击、输入、等待、刷新、关闭并重新打开页面、以及通过可见系统工具切换网络。

**禁止**：直接调用 API、修改数据库、注入回复、运行验证脚本、代替执行器推进状态。

- 遇到卡点**先留证**（截图/录像 + 时间），不边测边改。
- 本轮只做**当前版本体验记录**；修复之后另做复测，保留原始失败。

## 三、环境准备（执行方做，关键：不创建 run）

1. 启动 Robosuite Service（独立进程，`--enable-sim-gt`，端口 8082）。
2. 启动 UI server：`python -m benchmarks.attention_harness.ui_server --store <新 store> --artifact-root <目录> --run-catalog <合法 catalog> --robosuite-url <service> --camera-name agentview`（不用 `--demo`）。
3. 确认 run-catalog 里有**合法可选的 run 配置**（任务/seed/策略/预算），使"从 UI 创建 run"成为可能——但**不替你创建 run**。
4. 报告 UI 地址 + 相机连接状态给真人。

**判定**：准备结束时应该**只有服务、相机连接、启动选项**，没有已启动的 run。任何"配置失败 / 启动失败"都算结果，如实记录。

## 四、测试场景（先正常，后异常；逐个分开）

| 场景 | 实际操作 | 判断重点 |
|---|---|---|
| ① 正常闭环 | UI 配置启动 → 求助 → 阅读证据 → 输入普通中文建议 → 提交 → 看下一次执行及结果 | 输入是否保留；回复是否明确提交；是否解释采纳情况 |
| ② 受支持提示 | 另一次 run，通过 UI 输入系统声明支持的提示格式 | 验证接收和控制消费链路；不能代替普通语言体验 |
| ③ 延后与超时 | 点"稍后处理"；另一条请求一直不回答、超过 deadline | 截止时间是否清楚；是否 fallback；回复来源是否明确 |
| ④ 取消与重复操作 | 取消请求；双击提交；超时后再提交；第二个标签页处理同一请求 | 是否重复计费/重复执行/覆盖回复/留下错误状态 |
| ⑤ 主动中断 | 机器人运动期间点 run 中断 | 区分"已请求停止"与"已确认停止"；确认后是否继续运动 |
| ⑥ 恢复 | 等待回复和执行期间刷新、关闭重开；有条件再重启 UI 服务 | 请求、回复、配置、trace 是否恢复；是否重复启动 |

- **approval 批准/拒绝**另列场景。如果现有 UI 路径无法自然触发，记录"**未覆盖**"及原因；**不能后台造一条请求算通过**。

## 五、"采纳"分层判断（最重要）

对每一次"人工回复是否被采纳"，**分别记录四层**，前三层不能相互代替：

1. 回复**提交成功**；
2. 回复**关联到了下一次 attempt**；
3. 回复**导致实际动作变化**；
4. 变化后**原生任务是否成功**。

- 动作变化 **不保证** 任务成功。
- UI 上的 **ADOPTED 标签只能当作待核对的显示**，不能当作"已采纳"的证据。
- 应通过 UI 的回放、动作记录或 trace 核对实际行为；必要时用相同 seed、相同基础控制版本及其余设置的独立运行作对照。
- 如果 UI 没有提供足够证据，结论就是"**通过 UI 无法确认动作采纳**"——这本身就是一个**可观测性缺口**，要记下来。

## 六、交互检查清单（真人视角才会暴露）

- 输入 hint 时自动刷新是否**清空文字 / 丢失焦点**？
- 看回放时是否被刷新**打断**？
- 切换 run 后，回复是否仍**绑定正确请求**？
- 断网后是否把**旧画面继续显示成实时画面**？
- 错误提示是否足够明确，用户能否知道**下一步怎么做**？
- 等待真人期间：是否出现**机器人动作**？（约束：只允许 ≤8 项只读证据索引，`robot_actions=0`，见 `core/store.py:251`）

## 七、证据记录格式（每条固定）

```
时间（北京时间）/ run ID / request ID
→ 点了什么、输入原文
→ 预先期望
→ 实际看到什么
→ 截图 或 连续录像
→ 判定：通过 / 失败 / 证据不足 / 未覆盖
```

- 关键阶段用**连续录像**保留时间顺序；具体异常用**截图**。
- **不能**把"未复现""没触发""看不出来"写成通过；**不能**用某一次机器人成功替整个 workflow 背书。

## 八、判定规则

- **通过**：实际行为与预期一致，且有原始证据。
- **失败**：实际行为与预期不符。
- **证据不足**：UI 没有提供足够信息让我确认，明确说明缺什么。
- **未覆盖**：该能力在当前 UI 路径下无法自然触发，说明原因。

## 九、本轮边界

- 本轮只做**当前版本体验记录 + 与方案的核对**，不修 bug、不跑后台脚本、不自动推进状态。
- 修复之后另做复测；原始失败全部保留，不与修复后结果合并。
