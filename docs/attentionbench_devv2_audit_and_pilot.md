# 按 Dev v2（方案 A）重新审计，以及开发集小验证设计（2026-10-16）

范围：OpenArm365 / RoboCasa365，主实验引擎为 Dev v2（Dev agent 写代码 + Eval agent 复盘 + Advisor 求助）。
方法：读 `dev_experiment.py`、`dev_v2_loop.py`、`dev_help.py`、`dev_report.py`、`dev_configuration.py`、GPT 的验收文件和场景报告，并用临时账本干跑小验证的选择文件。**没有启动模拟器，没有任何付费调用。**

证据标记：「本轮读码」= 本轮直接读了代码；「本轮实测」= 本轮产物对比；「文档」= 来自已有验收文件，未重新验证。

## 1. Dev v2 引擎怎么工作（读码）

- 实验 = 任务 × seed × 策略 的 cell。每个 cell 里 Dev agent（`parcc/GLM`，温度 0，`max_tokens` 8192）一版版写完整策略源码，沙箱执行，独立评测。所有策略共用同一个 cell 预算、同一个 Dev 模型、同一份初始源码。
- 每版执行后，策略只看到**公开反馈**（错误、动作轨迹），决定下一版前是否求助。SDK 里**没有登记任何完成信号**，所以公开失败规则是“没有声明完成就算失败”，策略总会看到失败；是否真成功只在离线报告里由独立评测器读。
- 求助最多 `help_budget`（0–2）次。hint 由 Advisor 生成并放入下一版 Dev 输入。`demo_first` 的“demo”是任务的初始策略源码（事先写好，不带成功声明），不是视频。
- 成功的定义（`dev_report.py`）：cell 内**任一版**经独立评测为原生成功；另报终版成功、首次成功的版本号与耗时。分母保留所有计划 cell，未评测/未知不算失败；Wilson 95% 区间按任务×策略分组。
- 执行是串行的；整个实验有不可变清单（manifest）、身份锁、预算文件（绑定清单 SHA、账本路径），资源按“预留—结算”记账并可由收据重算。
- 报告自己声明：“Engineering small sample … 不能判断策略优劣”，并在每个任务×策略评测不足 5 个或全失败时，明确写“不排名”。

## 3. 关键发现

1. **同 seed 的初始场景不一致（阻塞，公平性）。** 文档记录水槽任务 5 次重置对比为 [匹配、失配、失配、失配、匹配]，目标物体 y 差 1.18 米。**本轮独立复现**：冒烟的三次 seed 101 重置，attempt2 的目标物体在 y=-2.3935，attempt3、4 在 y=-1.211（差 1.1825 m，与历史数值一致）。也就是说同一个“任务×seed”会落到不同的物理场景，策略之间不再是公平比较。Dev 引擎已有 `scene_contract` 机制能把失配的执行标为 `condition_invalid`，但现有配置**都没有启用它**（本轮干跑确认），且柜门的 D3 从未跑过。根因“未完全核实”。
2. **完整规划器在普通矩阵里被削弱。** approval 被拒、interrupt 不可达、Memory 为空，等待期工作只在专用通道。若主矩阵走普通通道，“核心方法”与 `trace_aware_hint_only` 的差别只剩 inspect-trace。若要保住三功能，只能走完整规划器专用通道，但那条通道的真实验收是“部分完成、受阻”。
3. **没有缓存与重复。** AdvisorProxy 的“相同条件可复现”目前靠温度 0。
4. **准入机制缺失。** Dev 通道结果永远是 `formal_eligible=false`。要把它当主实验数据，需要定义冻结、签字与准入的方式。
5. **成本被低估。** 见 §4。

## 5. 开发集小验证设计（尚未运行，需你授权）

**目的**：回答“能不能开始测”，不是比较策略。不计入结果，`formal_eligible` 保持 false。

**选择文件**（已用临时账本干跑校验通过，`outputs/devv2-pilot-design-20261016/selection.json`）：

```json
{"request_key": "pilot-20261016-a", "mode": "experiment",
 "tasks": ["pick_place_counter_to_sink", "open_cabinet"],
 "seeds": [101, 102, 103],
 "policies": ["autonomous", "reactive_help", "full_trace_aware_attention_planner"],
 "help_budget": 2, "max_versions": 3, "target_depth": 3,
 "target_valid_executions": 3, "coverage": "strict_full_depth"}
```

**为什么是这三种策略**：`autonomous` 是零求助的下限；`reactive_help` 在每次失败后都求助，是“求助最多能帮多少”的上限；完整规划器是核心方法（普通通道，缺三功能，见 §3-2）。三者之间如果连上限都没有成功，说明没有空间。
**为什么是 2 任务 × 3 seed**：共 18 个 cell。同一个（任务，seed）有 9 次重置，足够量化场景失配率。

| provider tokens | 3,216,096 | 0.1–0.5M（估算） |

| 执行墙钟 | 29,160 s | 约 2.5–4 小时串行 |

**事先登记的判定规则（跑之前写死）**

| 编号 | 规则 | 结果含义 |
|---|---|---|
| R1 空间 | 18 个 cell 中至少 1 个出现独立评测的原生成功 | 是：可以设计主矩阵。否：停止，用失败分类定位根因（环境、SDK 原语还是策略），再决定改任务、改 SDK 或加部分进度读数 |

## 6. 建议顺序

1. 小验证（本节），回答有没有空间。
2. 场景失配的根因调查（只用模拟器，不花 token）。可以和小验证的 R2 数据互相印证。
