# Guidance adoption v1.1 — RoboCasa execution-consumption correction

This amendment is frozen before its implementation and before its two real-Service arms, within the original 20-attempt/90-minute development limit. The original design, v1 byte streams, all executed v1 arms, and their failures remain intact. It does not open another validation round or change the original gates.

Code inspection found that RoboCasa AgentServerActionBackend.set_gripper validates settle_steps but submits the same gripper.open()/close(speed=64) job for every permitted value. Therefore changed settle_steps in an SDK trace is exposure/compilation only, not an executed control difference on this backend. Its baseline seed101 also stops at a read-only unreachable hover plan before issuing the modified grasp-height command. No adoption or success claim may be made for that v1 Memory arm from those parameters alone.

The revised RoboCasa recipe for existing text containing `verify approach and grasp success` and `get_observation` additionally compiles `base_forward_m=0.11`. This selects the existing shorter initial approach used by the valid hint arm: two initial forward commands become 0.11m instead of 0.125m, followed by the original reobserved planning loop. The mapping is a fixed cautious approach recipe, explicitly content-triggered. Its causal marker is the changed submitted and completed base job, not ignored gripper cadence or any native verdict. No other RoboCasa control source changes; no-guidance calls remain byte-for-byte equivalent at the SDK level. Native success is not expected or forced; this arm may still fail at the read-only arm plan and must report that honestly.

Robosuite keeps the exact already-tested v1 policy bytes. The final package version is guidance-adoption-v1.1 and separately freezes the pair (Robosuite v1 SHA, RoboCasa v1.1 SHA). Prior approvals and independent admission signatures cannot apply. The original 18-arm plan leaves exactly two slots: revised RoboCasa no-guidance and revised RoboCasa Memory with the same seed101/config/Services. Both are audited as same-policy arms. Final approval remains a new external decision bound to this pair and the package manifest.

Settling directives are retained for input compatibility but never counted as RoboCasa actuator changes. At this stage, not all compiled parameters are consumed by all backends; the audit must name which parameters led to completed backend commands. This limitation is explicit and is a future design cleanup, not a reason to inflate adoption claims.
