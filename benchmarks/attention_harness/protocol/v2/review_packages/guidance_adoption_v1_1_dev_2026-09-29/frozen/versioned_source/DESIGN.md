## Acceptance and scope

Both base policies must consume the existing public attention_input, inside the existing sandbox, without adding worker imports or relaxing Safety. Absent, empty, unsupported, or invalid guidance must produce the original no-guidance SDK calls exactly. No simulator/evaluator/Safety source or existing chain/profile/depth/admission gate is changed. All outcomes, including invalid or failed attempts, remain in the ledger. No held-out, 350-slot matrix, Memory promotion, or Safety fault injection.

Development execution is capped at 20 real formal-runner attempts, seed 101 only, two original task/scene/configs. Each attempt uses the existing dedicated Service, independent Safety, native evaluator, four SHA artifacts and process-group cleanup. Stop new execution on the first unsafe/unknown action or before the 90-minute deadline (2026-09-30 05:08:24 UTC); leave at least 10 minutes for cleanup/reporting. Native failure without uncertain action remains a valid outcome. No automatic new round. Offline deterministic tests may examine additional public observations but are not native-success evidence.

## Three paths into control

1. **advisor_guidance / hint**: deterministic, bounded text compiler. Recognized `AB_CONTROL_V1 key=value;` directives select a small whitelist of bounded numeric control parameters. Robosuite: grasp_offset_m, approach_tolerance_m, close_settle_steps. RoboCasa: grasp_offset_m, base_forward_m, open_settle_steps, close_settle_steps. Unknown keys, duplicate keys, invalid numbers or out-of-range values reject the entire directive and leave the baseline. A documented exact text recipe also recognizes existing natural-language advice: Robosuite text containing `lower it`, `grasp height`, and `gripper` selects center+0.005m grasp, 0.004m observed/controller tolerance, and 30 close ticks. RoboCasa text containing `verify approach and grasp success` and `get_observation` selects center+0.045m grasp, 20 open ticks and 30 close ticks. These are finite, explicitly specified phrase-to-recipe mappings, not general language understanding. Mere presence or ID of guidance selects nothing.

2. **demo_prior**: parse the existing verified public JSON projection with a policy-local bounded JSON reader (no eval, imports, asset file reads, or execution of text). Consume only whitelist SDK trajectories. Robosuite accepts the five-stage open/approach/grasp/close/lift sequence, extracts offsets and controller/settle parameters from its numbers, and retargets it to the current public cube. The reference cube center is the demo approach Z minus 0.12m; all three targets retain the demo relative XYZ geometry and order. The existing observed, segmented approach routine executes these targets, with demo tolerances, max_steps and settle ticks. RoboCasa accepts a bounded initial base-motion prefix followed by the two existing orientation deltas; base-prefix numbers change the actual initial route, while all later planning and public grasp/lift checks remain. Validate the entire supported trajectory before any adopted action. Unsupported video-only/other trajectories remain exposure only. A verified trajectory identical to the baseline plan may be consumed but does NOT pass observable adoption. Development modified demo fixtures are explicitly labelled authored SDK priors, not recordings of a successful robot demonstration.

3. **memory_guidance**: iterate only memory_ids_to_use, compile their corresponding text through the same content compiler. In real scheduler execution the existing gateway must retrieve a trusted applicable exact version and grant the next attempt before supplying text. An ID with absent/unsupported text changes no actions. No retrieval, authority, scope, expiry, promotion, or grant semantics are changed by the controller. Direct paired input fixtures prove the controller path only; at least one scheduler run must separately verify retrieval/grant-to-next-attempt provenance before claiming the full Memory path.

Precedence for an individual parameter: baseline < valid demo < recognized Memory texts in sorted selected-ID order < valid advisor text. Reject invalid inputs atomically for their own source; retain earlier valid sources. Missing fields never overwrite earlier values. No branch on native success, task verdict, seed, grant existence, request count or approval boolean. The parser returns numeric parameters/waypoints, never a success flag.

## Exposure versus adoption and causal evidence

Exposure is input persistence. Compilation is accepted parameters. Adoption requires a changed **completed SDK motion/gripper command** and a changed executed backend control sequence against the same-policy no-guidance arm, with equal seed, scene/object/config/Safety/Service identities and reset/initial-observation attestation. Use commands stripped of timestamps/IDs and compare backend action arrays, not only receipt text. Report first divergence and source text/trajectory SHA, relevant parameter and call arguments. Ablate the triggering content or change a numeric value under the same policy to establish content attribution. Memory IDs/grants alone, unsupported text and identical demo plans cannot count as adoption.

At least one valid paired real-Service case must change service_native_success from false to true while independent unsafe_attempts stays zero. All native verdicts are evaluator artifacts, never authored booleans. If action changes but native success does not improve anywhere, acceptance FAILS as a design issue. Report per-source and per-suite coverage honestly; bounded fixtures are not population effect estimates or a seven-condition frontier.
